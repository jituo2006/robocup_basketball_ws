# 调试界面全流程手册（`tools/console.sh`）

> 界面地址：**http://127.0.0.1:8090**
> 启动：`bash tools/console.sh`（默认 8090；**务必在 `boot.sh` 之后启动**）
>
> 本手册对应的版本：界面已消灭"假信息"，所有实时值都带年龄、可验证新鲜度。

## 1. 首次上电：全流程指令

### 步骤 1 —— 确认物理连接（**先做这步，软件救不了物理**）

```bash
# 雷达网线 + 电源（最高频的"假软件故障"）
bash tools/lidar_net_check.sh
#   carrier = 1 ✓  有链路
#   carrier = 0 ✗  【雷达没上电 / 网线松】← 去查线，别折腾软件
```

界面上对应位置：状态胶囊里的 **「雷达 链路OK/断开」**。

### 步骤 2 —— 启动整套

**方式 A（推荐，命令行）**
```bash
bash tools/boot.sh          # 约 50 秒，含雷达网卡自愈
bash tools/console.sh       # 然后浏览器打开 http://127.0.0.1:8090
```

**方式 B（界面上点）**
```
点「▶ 启动整套」→ 左侧「系统」卡片出现流程进度（flowbox）
```
> ⚠️ 两种方式都行，但**别同时用**：会产生重复节点。
> 界面现在会如实报 `重复节点`（超过应有数量才算重复，双摄的 2 个相机是正常的 ✓）。

### 步骤 3 —— 看"数据新鲜度"条，确认每一路都活着

界面顶部第二条，从左到右：

| 格子 | 含义 | 正常值 |
|---|---|---|
| 定位位姿 | `/localization/pose` 到达时刻 | ≤ 1.0s |
| 视觉检测 | `/perception/detections` | ≤ 1.5s |
| 前摄画面 | `/camera/image_raw/compressed` | ≤ 1.5s |
| 后摄画面 | `/camera_rear/...` | ≤ 2.0s |
| 雷达点云 | `/cloud_registered_body` | ≤ 1.5s |
| 雷达里程计 | `/Odometry` | ≤ 1.5s |
| 任务状态 | `/mission/status` | ≤ 2.0s |
| 机构OK / 机构状态 | `/rb_launcher/ok` 等 | ≤ 3.0s |

**颜色规则**：绿 ✓ 新鲜 / 黄 接近超时 / **红 ✗ 已过期（该路数据不可信，不能据此判断）**
**"从未"** = 这个话题一帧都没收到过。

> 这一条就是用来 **防止被假信息骗** 的：数据过期时格子变红，
> 界面不会拿最后一帧的旧值假装正常 ✓

### 步骤 4 —— 看「🎯 找球全流程」面板

| 行 | 看什么 | 异常怎么办 |
|---|---|---|
| ① 节点 | 定位/底盘/感知/任务是否都在，相机几个 | 缺哪个就点「⚡ 一键启动流程」 |
| ② 定位 | 位姿年龄 + 当前 (x, y, yaw) | 红色 → 定位节点没出数据 |
| ③ 视觉 | 检测年龄 + 检出数 + **认出几个球** | 红色 → 感知节点问题 |
| ④ 雷达 | 点云/里程计年龄；网卡无载波会直说 | 无载波 → `tools/lidar_net_check.sh` |
| ⑤ 雷达找球 | 候选数 + 测距 reason | 见 §4 排查 |
| ⑥ 找球脚本 | 是否在跑 | —— |

### 步骤 5 —— 就绪检查

```
界面上点「✓ 就绪检查」  ← 等价于命令行 bash tools/check_ready.sh
```
结果在「就绪检查」卡片里，**每一项都是现场真查的**（节点/话题/新鲜度/CAN）。

### 步骤 6 —— 点动试车（确认底盘能听指令）

界面上点动按钮，或：
```bash
python3 tools/teleop_chassis.py       # 键盘遥控
```
> 界面点动用的是**临时** `/cmd_vel` 发布者：按下才建、松开就销毁 ✓
> 这样不会一直占着 `/cmd_vel` 把找球脚本的独占检查搞挂 ✗

## 2. 找球：完整操作

### 2.1 命令行（推荐，输出最全）

```bash
# 只跑找球，跳过绕场
python3 tools/test_perimeter_ball.py --skip-perimeter --takeover --yes

# 先空跑一遍看前置条件（不动车）
python3 tools/test_perimeter_ball.py --skip-perimeter --dry --yes

# 完整流程（绕场一圈 → 找球 → 到球前 0.60m → 背对球）
python3 tools/test_perimeter_ball.py --takeover --yes
```

| 参数 | 作用 |
|---|---|
| `--skip-perimeter` | 跳过绕场 |
| `--takeover` | 自动 SIGTERM 掉 mission_node（它也会发 `/cmd_vel`） |
| `--yes` | 不问确认 |
| `--dry` | 只检查前置条件，不动车 |
| `--stop-distance` | 到球距离（固定 0.60 m） |
| `--search-wz` | 原地转圈角速度（默认 0.4 rad/s） |
| `--search-timeout` | 找球超时（默认 40 s） |
| `--no-search` | 跳过转圈找球 |

脚本的 5 个阶段（界面「⑥ 找球脚本」会跟着走）：
```
[1/5] 检查节点        → 需要 底盘/定位/感知/FAST-LIO 四个
[2/5] 接管 /cmd_vel   → mission 在 IDLE 也会发零速，会抢话题
[3/5] 读位姿与场地
[4/5] 原地转圈找球    → 球在车后也能找到
[5/5] 走到球前 0.60m → 必要时转 180° 用后摄/雷达精定位
```

### 2.2 界面上点

```
「🔍 寻球」按钮  →  实际执行 tools/test_perimeter_ball.py --skip-perimeter --takeover --yes
输出会实时滚进【日志面板】（TOOL 前缀）
同时【🎯 找球全流程】面板 ⑥ 会显示"运行中"
```

## 3. 双摄 + 分别调曝光

界面中列 **「📷 双摄画面」**：左前摄、右后摄，**各自独立**控制。

```
┌──────────────────────┬──────────────────────┐
│ 前摄 24.4 Hz         │ 后摄  7.4 Hz         │
│ [实时画面]            │ [实时画面]            │
│ 曝光 自动 · 曝光92 · 亮度113                          │
│ ☑自动 ▬▬●▬ 115      │ ☐自动 ▬▬●▬ 115      │
│ 手动  ▬▬●▬ 150      │ 手动  ▬▬●▬ 150      │
└──────────────────────┴──────────────────────┘
```

- **拖动滑块 / 勾自动** → 立刻下发（不用点"应用"）
- **自动** = 按"目标亮度"闭环调曝光（画面平均亮度 0~255）
- **手动** = 关掉自动后用固定曝光值（1~1200）
- 状态每秒回报一次，稍等就刷新成相机**实际值**（不是你以为设的值）✓

命令行等价操作：
```bash
# 看两个相机的真实曝光状态
curl -s http://127.0.0.1:8090/api/exposure | python3 -m json.tool

# 前摄：目标亮度改 80（画面变暗）
ros2 topic pub --once /rb_camera/exposure_cmd \
  std_msgs/msg/String "{data: '{\"target\": 80}'}"

# 后摄：关掉自动，固定曝光 300
ros2 topic pub --once /rb_camera_rear/exposure_cmd \
  std_msgs/msg/String "{data: '{\"auto\": false, \"value\": 300}'}"

# 看回报
ros2 topic echo /rb_camera/exposure_state --once
# → {"node":"rb_camera","auto":true,"target":80,"value":128,"mean":110.3,"ok":true}
```

> 两个摄像头的配置可以**照抄同一套** ✓（`camera.yaml` / `camera_rear.yaml` 结构一致）

## 4. 雷达云点图 & 小球显示

界面中列 **「📡 雷达俯视图」**：
- 云点图 + 场地边框/中线/三分线/投篮线/传球区
- **识别出的球会画成黄色圆环 + "雷达球 X.Xm" 文字** ✓
- 需要先在「雷达找球」卡片里**启用**（默认关：连订阅都不建，行为与改动前一致）

```bash
# 雷达数据够不够新（决定找球能不能精定位）
python3 tools/check_lidar_latency.py
#   判据：自身年龄 ≤0.3s，云↔里程计时间差 ≤0.10s

# 云点图不顺畅 / 延迟大 → 打补丁（默认 dry-run）
bash tools/apply_lidar_patch.sh
bash tools/apply_lidar_patch.sh --apply     # 真改 + 重编译 fast_lio
```

**为什么雷达会不顺**（实测数据）：FAST-LIO 订阅队列原来写死 20，
雷达 10Hz → 积压 20 帧，实测 `/Odometry` 中位年龄 **1.379s** ✗；
找球要求 ≤0.3s ⇒ 永远判 stale ⇒ 车不动。
补丁把它改成可配（默认 5）并关掉累积地图（`map_en: false`），
改完后中位 **0.024s** ✓（快 57 倍）。

## 5. 日志面板

- 来源三合一：`boot.sh` 输出、工具 stdout、ROS `/rosout`
- 前缀：`LAUNCH`（整套）/ `TOOL`（调试工具）/ `INFO/WARN/ERROR`（ROS 节点）
- **跑找球时，脚本每一行都会滚进来** ✓ 这正是给"分析为什么乱"用的

```bash
# 想把日志存下来慢慢分析
bash tools/console.sh > /tmp/console.log 2>&1 &     # 控制台自身日志
# 另外单独抓速度指令（分析"运动乱"最有用的）
ros2 topic echo /cmd_vel > /tmp/cmdvel.log
```

## 6. 运动时排查"乱"的标准动作

```bash
# 终端 A：抓速度指令
ros2 topic echo /cmd_vel > /tmp/cmdvel.log

# 终端 B：跑找球
python3 tools/test_perimeter_ball.py --skip-perimeter --takeover --yes

# 终端 C：同时在界面看
#   ① 新鲜度条：定位/雷达是否一直绿
#   ② 找球全流程：⑥ 走到哪一步、⑤ 雷达候选
#   ③ 日志面板：脚本逐行输出
```

对照判断：
| 现象 | 看哪里 | 常见原因 |
|---|---|---|
| 一顿一顿 | `/cmd_vel` 是否断续 | 发布间隔 > 底盘 200ms 超时 |
| 走不直/画龙 | ② 定位 yaw 是否跳变 | 定位数据过期（格子变红） |
| 到点不停 | ③ 视觉/④ 雷达年龄 | 数据过期 ⇒ 脚本拒绝动 |
| 转圈找不到球 | ③ 视觉"球 N 个" | 球没认出来 / 曝光不对 |
| 雷达候选 0 | ⑤ 雷达找球 reason | `stale_or_unsynchronised` 等 |

## 8. 界面"不会骗你"的设计说明

| 机制 | 作用 |
|---|---|
| 每路数据带 `*_stamp` | 节点停掉后能看出"数据是 N 秒前的"，而不是显示一个静止的旧值 |
| `fresh` / `fresh_limits` / `stale` | 后端算出年龄与阈值，前端据此染色 |
| 检测过期自动清空 | 感知停了不会还挂着上一帧的 `rack_ring` 列表 |
| `node_dup` 只在**超过应有数量**时报 | 双摄的 2 个相机/感知是正常的 ✓ 不再误报 |
| `node_missing` 新增 | 0 个节点才是真问题，原来完全没显示 |
| `hw.cam_front/cam_rear` 查 by-id | 不再用 `/dev/video0` 瞎猜（插拔顺序会变） |
| 硬件体检走 TTL 缓存 | `/api/state` 从 **1.067s → 0.03s**，界面才能真的每秒刷新 |
| 雷达候选走后台线程 | 点云处理 ~1s 不再计入请求耗时 |
| `/api/exposure` GET 读相机回报值 | 显示的是相机**实际**曝光，不是你设的值 |
