# 底盘上电握手与无通信超时策略

主机代码需要配套支持本协议的DJI板端固件；旧固件不会回复握手，底盘将持续等待。

## CAN协议

标准帧，板号1~3。请求ID为0x200+板号，响应ID为0x280+板号，DLC均为8。
请求布局：motor(uint16 LE)、opcode(uint16 LE)、value(uint32 LE)。
- motor=0、opcode=0x70：查询，value为本次nonce。
- 响应byte0为0xB1（未确认）或0xB2（已确认）；byte1为速度模式掩码，byte2为使能掩码，byte3为已收到电调反馈掩码，byte4~7回显nonce。
- 四路反馈出现后，主机逐个补齐缺失的速度模式/使能，避免反复MotorOn重置PID。
- 三个掩码均为0x0F且未确认时，motor=0、opcode=0x71携带同一nonce完成确认；板端清零速度目标，一次性消费挑战。
- 确认前不发送运动速度；确认/明确复位后清除旧目标，收到新零速后才允许运动。
- 每100ms轮询/重试，忽略ID、长度、类型或nonce不匹配的响应。

## 用户选择的无超时行为

/cmd_vel最后有效值不按消息年龄清零。板端握手状态、有效定位、检测消息也不因静默时间失效。
任务到点、转向、定位就绪和找球等待没有固定总截止时间；仍需实际测量确认到点/停稳。
手动急停、显式零速、明确输入错误/故障以及报告的板端复位继续处理。
因此发布进程断开时，最后非零速度不会仅凭时间自动停止。
旧cmd_vel_timeout_ms及相关年龄参数保留兼容，不再触发超时停车。
机构动作保持时长、轮询等待和独立机构确认流程不属于被删除的底盘/导航停车截止时间。

## 兼容与部署

本次握手不替换既有CAN底层发送实现；内核/驱动故障仍应单独诊断。
配套DJI固件的CAN提交应立即尝试，避免持有电机锁等待邮箱；初始化和锁修复也在板端。
更新主机源码或编译不会自动烧录控制板。未烧录配套固件前，不能将底盘等待握手当作通信已通过。

## 验证

board_link与omni_kinematics由CTest运行；Python单元检查覆盖导航、定位及无超时策略。
测试使用模拟数据，不执行真实运动。实车上电顺序及无扭矩问题仍需配套固件烧录后的现场验证。
