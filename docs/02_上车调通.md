## 阶段 1 · 底盘（最先做，风险最低）

### 1.1 拉起 CAN

```bash
sudo ip link set can0 down 2>/dev/null
sudo ip link set can0 type can bitrate 1000000
sudo ip link set can0 txqueuelen 20        # ⚠️ 不能省，见下方说明
sudo ip link set can0 up
ip -details link show can0                 # 要看到 UP / ERROR-ACTIVE / bitrate 1000000 / qlen 20
```

> ⚠️ **`txqueuelen 20` 不能省。** 内核默认 1000，长队列会积压旧速度帧，导致
> "发了指令当时不动、随后突然窜车"。这是 2026-07-08 那次**紧急断电事故**的成因。

### 1.2 量车体参数（**必须做，别抄旧值**）

用卷尺量，填进 `src/rb_chassis/config/chassis.yaml`：

| 参数 | 含义 | 怎么量 |
|---|---|---|
| `width` | 轮距（左右轮中心距） | **不是车宽**，是两个轮子中心的距离 |
| `length` | 轴距（前后轮中心距） | 同上 |
| `wheel_radius` | 驱动轮半径 | 直径 ÷ 2 |
| `ratio` | 减速比 | **保持 1.0**（原代码此项无效，改了会整体偏） |

> ⚠️ 当前配置里的 `0.40 / 0.40 / 0.10` 是**占位值**。
> 量错了会表现为"直行速度不对、转向偏得离谱"。

### 1.3 架空点动验证方向

```bash
ros2 launch rb_chassis chassis.launch.py      # 或 ros2 run rb_chassis rb_chassis_node
python3 /home/user/26_R1/scripts/r1_chassis_teleop.py --max-linear 0.10
```

| 指令 | 期望 |
|---|---|
| `w` | 向前 |
| `s` | 向后 |
| `a` | 向左平移 |
| `d` | 向右平移 |
| `j` | 逆时针（俯视） |
| `l` | 顺时针（俯视） |

**方向反了** → 改 `omni_chassis.cpp` 里对应项符号，重编译。
**某个方向不动** → 查那个电机的 CAN ID / 供电。

### 1.4 验收

- [ ] 6 个方向全部正确
- [ ] 按空格 / Ctrl+C 能立刻停
- [ ] 拔掉 USB-CAN 后车会停（200 ms 超时保护生效）

## 阶段 2 · 弹射机构

### 2.1 补 udev 规则（否则起不来）

`launcher.yaml` 默认用 `/dev/R1_usb2ttl`，本机没有这条规则：

```bash
ls -l /dev/serial/by-id/
udevadm info -q path -n /dev/ttyUSB0       # 查物理口
```

两种做法：
- **推荐**：补 udev 规则生成 `/dev/R1_usb2ttl`（保持与上一届一致）
- **快速**：改 `launcher.yaml` 的 `port:` 为实际设备名

### 2.2 分动作测试（**从行程最小的开始**）

```bash
ros2 launch rb_launcher launcher.launch.py
ros2 topic echo /rb_launcher/ok            # 应为 true

# ① 先测夹爪开关（行程最小、最安全）
ros2 service call /rb_launcher/launch rb_msgs/srv/Launch "{action: 4, speed: 0, angle: 0}"
# ② 再测滑轨
ros2 service call /rb_launcher/launch rb_msgs/srv/Launch "{action: 5, speed: 0, angle: 0}"
# ③ 最后才测发射（⚠️ 确认弹道前方无人！）
ros2 service call /rb_launcher/launch rb_msgs/srv/Launch "{action: 0, speed: 2800, angle: 64}"
# 停止重复发送
ros2 service call /rb_launcher/launch rb_msgs/srv/Launch "{action: 7, speed: 0, angle: 0}"
```

> action 取值：0=发射 1=快速发射 2=运球 3=两次运球 4=夹爪开关 5=滑轨开关 6=保持循环 7=停止

### 2.3 验收

- [ ] `/rb_launcher/ok` 为 true
- [ ] 夹爪、滑轨、发射三个动作都能被驱动
- [ ] 下位机回显没有未知命令的 `ERROR`

## 阶段 3 · 相机 + 视觉

### 3.1 起相机，确认话题

```bash
ros2 topic list | grep -i image
ros2 topic hz /camera/image_raw
```

若话题名不同，改 `perception.yaml` 或启动参数 `image_topic:=...`。

### 3.2 打开调试图，肉眼确认检出

```bash
ros2 launch rb_perception perception.launch.py publish_debug_image:=true
ros2 run image_transport republish raw in:=/perception/debug_image out:=/debug_view   # 或用 rqt_image_view
```

推荐用 **rqt_image_view** 看 `/perception/debug_image`：框对了才继续。

### 3.3 现场标定颜色（**必做**）

2026 新规要求识别"各队自带用球的颜色/图案差异"，**不能写死阈值**。

方法：
1. 把球放在实际场地的光照下，拍一张图
2. 用取色工具读出 HSV，替换 `perception.yaml` 里对应的 `hsv_ranges`
3. 每次改完立刻跑 `python3 tools/make_test_image.py --check` 确认没把其它类别带崩

### 3.4 标定相机内参

`fx/fy/cx/cy` 全为 0 时节点按"假定 60° 水平 FOV"估算 —— **只能用于能看到目标，不能用于测距**。
需要测距（判断"球多远""是否到吸取距离"）就必须用棋盘格标定后填真实值。

### 3.5 验收

- [ ] `/perception/debug_image` 里：目标球、篮筐、传球架圆环、定位柱都被框住
- [ ] 干扰球**没有**被误判成目标球
- [ ] 距离估计与卷尺实测误差 < 20%（标定后）

## 阶段 4 · 定位

### 4.1 先决定定位方案（**这是全项目最大的技术风险**）

| 方案 | 说明 | 合规性 |
|---|---|---|
| 全场定位板（上一届用的） | 外部系统，CAN 发位置 | ⚠️ **规则 §2.4 场地器材清单里没有它**，需先向技术委员会确认 |
| 雷达 FAST-LIO | 已有 `~/lidar_360` | ✅ 车载自主，合规 |
| 视觉定位柱 | 规则专门提供的视觉基准 | ✅ 合规，但需要定位柱在视野内 |

**建议**：以雷达为主，用定位柱做校正；把定位板当"如果允许就用"的加速项。

### 4.2 配置输入源

`src/rb_localization/config/localization.yaml`：

```yaml
sources:
  odom_topic: "/odom"              # 提供 twist 做预测
  abs_pose_topic: "/Odometry"      # 雷达 FAST-LIO 的绝对位姿；留空则不启用
  use_odom_pose_as_abs: false      # 若 /odom 自带绝对位姿（定位板）就设 true

landmarks:                         # 本轮定位柱的实际坐标（场地坐标）
  - {x: 3.5, y: 2.0}
```

> ⚠️ `landmarks` 为空时，视觉方位角更新**不会生效**（节点会明确告警）。

### 4.3 验证

```bash
ros2 launch rb_localization localization.launch.py
ros2 topic echo /localization/pose        # 推车时 x/y/yaw 应跟着变
ros2 topic echo /localization/ok          # 应为 true
ros2 run tf2_ros tf2_echo field base_link
```

**关键检查**：把车推到场地某个已知点，看 `x/y` 是否与卷尺实测一致。
不一致就是坐标系原点/朝向定义问题，**必须先解决再上任务**。

### 4.4 验收

- [ ] 静止 30 秒，位置漂移 < 5 cm
- [ ] 推车走一圈回到原点，误差 < 20 cm
- [ ] 定位柱进入视野后，误差明显收敛

## 阶段 5 · 整车联调

```bash
ros2 launch rb_bringup bringup_full.launch.py
```

### 5.1 先空跑任务（不上球）

```bash
ros2 service call /rb_mission/set_mission rb_msgs/srv/SetMission "{mission: PASS}"
ros2 topic echo /mission/status
```

**观察**：状态迁移是否符合预期；机器人是否会往合理方向走。
**随时能停**：

```bash
ros2 topic pub --once /mission/estop std_msgs/msg/Bool "{data: true}"
```

### 5.2 再放球，逐个阶段确认

| 阶段 | 观察点 | 不对时改哪里 |
|---|---|---|
| `SEEK_BALL` | 会不会朝球走、会不会对准 | `perception.yaml` 颜色；`mission.yaml` 的 `max_linear` |
| `ACQUIRE` | 贴上去后是否判定吸到 | `close_lost_distance_m`、`acquire_seconds` |
| `NAV_TO_ZONE` | 是否走到动作区 | `field.pass_zone_target` / `shoot_zone_target` |
| `ALIGN` | 是否对准篮筐/圆环 | `kp_yaw`、`yaw_tolerance` |
| `LAUNCH` | 是否真的发射 | `rb_launcher` 是否 ok、`speed/angle` |
| `RETURN_HOME` | 是否回到出发区 | `field.home` |

### 5.3 调参顺序（**一次只改一个**）

1. `max_linear` / `max_angular` —— 先让动作慢而稳
2. `kp_linear` —— 走位是否过冲/太肉
3. `kp_yaw` / `yaw_tolerance` —— 对准精度
4. `position_tolerance` —— 到点判定松紧
5. 视觉阈值 —— 最后再动

## 出问题时的排查顺序

```
车不动？
├─ /cmd_vel 有数据吗         → ros2 topic hz /cmd_vel
│   └─ 没有 → /mission/status 卡在哪个阶段？该阶段是不是在等定位/视觉？
├─ 有数据，车不动            → can0 起了吗？txqueuelen 是 20 吗？电机使能了吗？
└─ 车动但方向不对            → 阶段 1.2 的尺寸参数、阶段 1.3 的方向验证

定位不对？
├─ /localization/pose 有输出吗
├─ /localization/ok 是 true 吗
└─ 静止漂不漂 → 漂 = 里程计噪声太大或绝对观测没生效

视觉看不到目标？
├─ /perception/debug_image 里能看到目标吗
│   ├─ 看得到但没框 → 颜色阈值不对（重标定）
│   └─ 看不到       → 相机曝光/视野问题，不是算法问题
└─ /perception/detections 有对应 label 吗
```
