# 自动比赛捡球与投篮串口流程（2026-10-16～17）

作用工程：远程 Linux `/home/user/robocup_basketball_ws`。三回合整轮和分阶段入口共用这里的自动流程。传球出球序列、场地坐标、路线及手动机构按钮保持原逻辑。

## 公共确认规则

- 每个步骤第一次立即发送；未收到有效确认时每 **50 ms** 重试，最多 **20 次**，确认窗口 **1 秒**。收到正确确认立即停止重发。
- 只有一个 ROS 串口服务请求在途；服务延迟时不补发一串积压请求。20 次是上限，服务未就绪或响应慢时可能少于20次。
- 使用唯一串口节点 `rb_launcher` 的 `/rb_launcher/text` 和 `/rb_launcher/rx_event`，任务本身不打开串口、不竞争接收数据。
- 同一步骤的重发属于一个确认组。缓存分包/连包回复，并区分串口连接代次、TX编号和事件顺序。其他控制源插入命令、连接改变、回复事件丢失时，本任务不继续发送新运动。
- 主板协议本身没有命令事务ID；主机边界不能完全消除线路上任意迟到回复的歧义。`DONE` 和 `home=1` 也不证明球实际入仓、投出或机械到底。
- ROS关闭、任务取消和底盘运动故障会退出流程，不在清理代码里启动下降、再次投篮或复位。

## 捡球

底盘后退靠近并停车后执行：

| 顺序 | 命令 | 有效确认 / 后续等待 |
| --- | --- | --- |
| 1 | `dji_stop` | `ACK DJI_STOP` |
| 2 | `dji_zero` | `ACK DJI_ZERO` |
| 3 | `dji_move 1 90 5` | `ACK DJI_MOVE 1 MOVING` 或 `HOMING`，停止重发，再等 `DONE`，最多15秒 |
| 4 | 无新命令 | 上升完成后等待 **1秒** |
| 5 | `dji_move 1 0 5` | 同上，独立等待下降 `DONE`，最多15秒 |
| 6 | `dji_stop` | `ACK DJI_STOP`，结束捡球流程 |

同一目标的 `ACK DJI_MOVE 1 HOLD` 表示主板已经在该绝对目标保持，视为完成，避免等待不会再生成的DONE。步骤3/5收到ACK后不再重发；等待完成期间积压的 `ERR BUSY` 不当作动作失败，`ERR FAULT` 则结束该步骤的完成等待。

按用户指定：普通命令错误/确认超时、动作完成超时，记录该步骤未确认，跳过该步骤并继续后面的命令和路线。若上升未确认完成，不额外等待1秒。`round_pickup_completed` 只表示序列已走完，`round_pickup_confirmed` 与 `pickup_report` 才表示各步骤是否确认；含跳过步骤不会标成全部成功。

串口服务请求本身超时属于“是否已经发送未知”，本进程不再排队新动作，后续步骤记录未确认，需检查串口节点并重新启动任务。

## 投篮（shoot任务，传球pass不变）

命令主体为：

```text
vesc_stop
vesc_home
vesc_shoot2 3
vesc_stop
vesc_reset
```

1. `vesc_stop` 按公共规则重发，确认 `--VESC stop: both 0 A mailboxes cleared; ...`。随后只在待机时查询 `vesc_status`，最多3秒，要求两路反馈新鲜（age<20 ms）、低速静止、请求0 A、pending=0、无主板锁存故障，连续确认至少150 ms。
2. `vesc_home` 同样重发，只有人工起点确认回复含 `encoder_home=1` 才继续。`encoder_home=0` 不能启动编码器闭环投篮。
3. `vesc_shoot2 3` 同样重发；收到 `--SHOT2 starting both; ...` 后立即停止重发，最多5秒等待本次新run的结果和多行报告结束。仅 `reason=timed release`、`timing_speed` 非 `INVALID`、无报告故障才继续。
4. 再执行 `vesc_stop` 确认与待机静止检查。
5. `vesc_reset` 同样重发；收到 `--RESET top assumed; ...` 后停止重发，最多5秒等新的 `RESET_RESULT FINISHED`，要求 `valid=YES`、`reason=timed release`、`fault_id=0`。
6. 另等最多5秒确认 `--RESET bottom zero established; home=1 ...`。通知丢失时，在复位结果结束后可通过 `vesc_status` 的待机 `home=1` 确认。
7. 正常完成后不追加 `vesc_stop`，因为当前主板的停止命令会清除刚建立的home。

准备失败、发射异常、复位异常或等待超时，都有界退出并记录失败；尽力发送停止并确认，**不盲目再次发射或从未知位置启动定时复位**。该投篮阶段返回未确认，原任务管理器保留失败进度，不报整轮成功；传球阶段仍走原配置。

`vesc_reset` 是主板定时回程。结果成功和home=1代表源码的时间假定，不是底部传感器检测。0 A仍为滑行。

## 计时回位与使用

保留现有计时回位策略，开始机构动作前预留完整的有界等待预算：捡球36秒，投篮32秒。若余量不足，先回位，不新开机构动作；动作已经开始则走完确认/失败退出后再由原计时器处理。不要把ACK的1秒窗口当成电机运动时间。

本次为Python主机逻辑调整，现有串口节点已提供RX事件及发送元数据，无需重编译C++。结束旧的任务进程，再从原比赛按钮/脚本启动新任务即可加载新模块；不自动重启真实服务，也不发送实机动作。

测试结果另见同目录的本次验证记录。只使用模拟MCU和独立ROS域的PTY，实机动作及机构到位仍待现场验收。
