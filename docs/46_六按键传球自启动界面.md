# 六按键传球界面：桌面手动启动与设备就绪检查

NUC 桌面显示 A/B 场地各回合 1/2/3，共六个动作按钮。页面沿用原控制台配色、大按键和输出面板，文件为 `tools/console_ui.html`。

## 执行方式

设备正常后，按钮启动 `bash tools/run_first_round.sh --start-point A|B`、`run_round2.sh` 或 `run_round3.sh`。起步等待由原脚本配置执行，UI 不重复等待。原有机构指令、运动实现、脚本内部检查和 SSH 直接执行方式保留。

## 前后端分离与脚本更新

前端只提交 `side`（A/B）和 `round`（1/2/3），不包含脚本名、路径、参数或等待时长。后端通过 `tools/pass_actions.json` 将 A1/A2/A3/B1/B2/B3 映射成命令参数列表，每次点击重新读取配置。

- 修改原脚本内容或路线参数：保存后下次执行生效，前端不改，UI 服务无需重启。
- 更换脚本名称、路径或参数：只改 `pass_actions.json` 对应项，下一次点击立即使用新命令，前端不改，UI 服务无需重启。
- 修改 Python 后端代码：只重启 `robocup-pass-console.service` 加载代码，前端不改。

例如 A1 可改为 `["bash", "tools/new_round1.sh", "--start-point", "A", "--some-option"]`。路径相对于工作空间根目录，也可填写绝对路径。直接按参数列表运行，不通过 shell 拼接命令。更新映射文件时可先写临时文件再原子替换，避免读取半份 JSON。

接口：`POST /api/pass/run` 接收 `{"side":"A","round":1}`，设备正常返回202及`{"id":"执行ID"}`；未就绪返回409和具体原因，不启动脚本。`GET /api/pass/state` 返回输出、状态及`hardware`。默认映射仍为原六种组合。

页面顶部显示雷达、底盘的正常/未就绪状态及具体原因。初次加载、网络中断或状态未确认时六按钮禁用；两项均正常才放行。后端在接收选择和真正启动子进程前各检查一次，防止切换路线期间状态变化。设备正常时仍可选择另一回合，旧路线退出后交接控制。页面保留脚本输出、真实退出码及刷新后的记录恢复。

设备检查订阅`/lidar/session`、`/localization/ok`、`/chassis/ready`和新增的`/chassis/status`，不以ping或can0 UP判定硬件正常。雷达需要新会话和有效定位；底盘需要真实模式、四路电调反馈/速度模式/使能握手及最近的有效板端应答。没有应答、反馈不齐、尚未确认速度模式/使能、模拟模式或监测程序异常都会说明原因。

界面设备状态超过2秒未更新就禁止新任务；底盘诊断要求最近1秒有匹配握手查询的有效应答。**仅用于新回合开始条件，不修改/chassis/ready的无超时语义，不新增运动指令超时停车，也不因界面失联结束活动路线。**

## NUC 安装与启动

```bash
cd /home/user/robocup_basketball_ws
bash tools/install_pass_console_desktop.sh
bash tools/open_pass_console.sh
```

安装器禁用并停止`robocup-pass-console.service`，关闭旧的桌面登录自启动，在`xdg-user-dir DESKTOP`指定的桌面（当前/home/user/桌面）放置“传球控制”快捷方式。开机和登录不启动该前端，也不会由此前端触发整车启动。点击快捷方式后，启动后端并用Chrome独立窗口打开`http://127.0.0.1:8090`。重复打开会复用同一个服务。

原命令`install_pass_console_autostart.sh`保留为手动安装器的兼容入口，不再开启自启动。安装前会备份原服务和桌面入口。PTP是独立系统服务，其开机启动保持不变。

手动只启动后端：`bash tools/start_pass_console.sh`。该脚本加载ROS及工程环境并设置ROS_DOMAIN_ID=2，使只读状态监测能接收设备消息。原综合控制台仍由`bash tools/console.sh`启动；两者使用同一默认端口，请勿同时启动在8090。关闭浏览器不会强行结束正在运行的路线，后台服务会保持到关机或手动停止。

## SSH 返回结果

原脚本从 SSH 执行仍直接输出日志、返回退出码。UI 后端也提供相同执行记录，SSH 中可查询：

```bash
# 只读查询最近一次执行，不启动运动
curl -s http://127.0.0.1:8090/api/pass/state
```

结果含 `id`、`side`、`round`、`status`、`returncode`、`lines`。可用 `/api/pass/state?id=记录ID&after=游标` 增量读取。UI 触发接口为 `POST /api/pass/run`，JSON 为 `{"side":"A","round":1}`，收到执行 ID 后查询至结束即可；接口启动真实运动脚本。

## 验证边界

检查覆盖六种原脚本映射、日志/退出码、设备状态组合、缺失/旧状态、模拟模式拒绝、六种回合API拦截、交接期间故障再次检查、网页初始/异常/断线禁用，以及安装器关闭两种自启动。原脚本执行测试只运行模拟命令；ROS订阅测试使用独立177域和localhost，不发布运动控制。界面实图和行为也使用模拟设备状态。没有因此执行真实比赛回合。


## 手动打开界面后准备设备

手动启动后端后才运行检测线程，默认每秒检查雷达网口和雷达可达性。主机和雷达可一起上电，底盘DJI板和四路电调可随后独立上电。雷达网络作为准备整车软件的信号；底盘是否就绪仍由板端回执独立确认。

启动命令、网口、雷达IP、检测周期仍在tools/pass_boot.json配置。默认命令bash tools/boot.sh start_mission:=false只准备整车节点；路线由设备正常后的六按钮显式触发，起步等待沿用原配置。

整车由robocup-pass-stack.service独立托管。UI重启或刷新复用已有整车实例；雷达未连接时等待，启动失败时继续重试。单纯ping丢包不重启整车；雷达网口carrier连续断开3秒后，重新连接时按既有逻辑重建整车程序。底盘独立断电不依赖此检测，使用配套CAN恢复和板端重新握手。

查看检测状态：curl -s http://127.0.0.1:8090/api/boot/state。查看真实 boot 输出：journalctl --user -u robocup-pass-stack.service -f。前端空闲时显示后台检测/启动状态，传球执行期间仍显示原有脚本输出与退出码。

查询设备状态：`curl -s http://127.0.0.1:8090/api/hardware/state`。`can_run=true`仅表示当前允许开始新回合，具体任务仍由脚本内部逻辑执行和检查。
