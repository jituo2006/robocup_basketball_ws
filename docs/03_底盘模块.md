# 03 · 底盘模块（rb_chassis）

全向轮底盘：订阅 `/cmd_vel`，运动学解算成四轮转速，经 CAN 下发。**已调通。**

---

## 1. 代码分层

```
rb_chassis_node.cpp     主函数：读参数 → 建对象 → 100Hz 主循环
   └─ OmniChassis       全向轮运动学 + DJI 电机控制
        ├─ Chassis      基类：订阅 /cmd_vel、限幅、超时判断
        ├─ DJIBoard     第三方库：CAN 协议封装（VelCfg/MotorOn/VelCtrl）
        └─ Can          第三方库：SocketCAN 收发（含防窜车补丁）
```

数据流：`/cmd_vel(Twist) → applyLimits() → 运动学解算 → wheel_speed[4] → VelCtrl → CAN`

## 2. CAN 上电与掉线恢复

### 2.1 首次上电

```bash
sudo ip link set can0 type can bitrate 1000000
sudo ip link set can0 txqueuelen 20        # ⚠️ 不能省，见下
sudo ip link set can0 up
ip -details link show can0                 # 要看到 UP / ERROR-ACTIVE / 1000000 / qlen 20
```

> ⚠️ **`txqueuelen 20` 不能省。** 内核默认 1000，长队列会积压旧速度帧，
> 导致"发了指令当时不动、随后突然窜车"——2026-07-08 紧急断电事故的成因。

**PCAN-USB 适配器识别**：`lsusb` 应看到 `PEAK System PCAN-USB (0c72:000c)`。

### 2.2 ⚠️ 拔插过 CAN 适配器之后（必须照做）

**拔插 CAN 适配器会毁掉当前所有 CAN 通信**，链条如下：

```
拔掉适配器
  → can0 接口消失
插回去
  → can0 被重新创建，但状态是 DOWN（要手动 up）
  → ⚠️ 接口编号也变了（实测 6 → 7）
  → 底盘节点的 CAN 套接字还绑在旧编号上 → 彻底失效，命令发不出去
  → 电机板这段时间收不到任何命令
  → 触发「通信超时保护」，把电机**锁存**在故障态
  → 即使 can0 恢复、节点重启、重新发 MotorOn，板子也**不会**自己解锁
```

**恢复四步（缺一不可）：**

```bash
# ① 重新拉起 can0
sudo ip link set can0 type can bitrate 1000000
sudo ip link set can0 txqueuelen 20
sudo ip link set can0 up
ip -br link show can0                      # 必须显示 UP

# ② 确认只有一个底盘节点（见 §6 教训 4）
pgrep -af "lib/rb_chassis/rb_chassis_node"

# ③ 重启底盘节点（让它重新绑定新的接口编号）

# ④ ⚠️ 最容易漏掉的一步：把电机板【彻底断电 10 秒】再上电
#    拔插 CAN 只断通信、不断电机板电源，故障锁存清不掉；
#    软件重发 MotorOn 也没用 —— 必须物理断电。
```

> 2026-10 实际踩过：can0 恢复了、帧发得出去、板子也 ACK（0 错误）、速度值也对，
> **但轮子就是不动 —— 卡在第 ④ 步。** 断电重启电机板后立刻恢复。

或者直接跑 `bash tools/can_recover.sh`，它自动做 ①②③ 并提示 ④。

## 3. 主循环三步（100Hz，`omni_chassis.cpp::execute`）

### ① 超时保护（防窜车核心）

```cpp
if (!hasFreshVelocityCommand()) {          // 超过 200ms 没收到新 /cmd_vel
    sendZeroVelocity();                    // 只发一次零速
    return;
}
```

命令一断（脚本崩/节点挂），200ms 内自动零速。

### ② 限幅 + 加速度限制（`base_chassis.cpp::applyLimits`）

```cpp
out.linear.x = std::clamp(out.linear.x, -limit_vel, limit_vel);   // 限速
// slew() 斜率限制：每周期最多变化 limit_acc×dt，防瞬间窜车
```

两个都是**移植时修的 bug**：原 2025 实现里 `clamp` 返回值被丢弃（限速从没生效）、
`limit_acc` 被设置但从未使用。

### ③ 全向运动学

```cpp
factor = 60/(2π·wheel_radius) · ratio     // m/s → 电机转速单位
c      = cos(45°)                          // X 布局，轮子斜 45°
arm    = hypot(width/2, length/2)          // 车中心到轮子对角线距离

wheel[0] = (+vx·c − vy·c − wz·arm) · factor
wheel[1] = (+vx·c + vy·c − wz·arm) · factor
wheel[2] = (−vx·c + vy·c − wz·arm) · factor
wheel[3] = (−vx·c − vy·c − wz·arm) · factor
```

- 纯平移：四轮按 `±vx·c ± vy·c` 组合。
- 纯旋转：四轮**同向同速** `−wz·arm`（X 布局原地旋转的正确特征，不是 bug）。
- 干跑实测：前进 `[13,13,-13,-13]`、左移 `[-13,13,13,-13]`、左转 `[-11,-11,-11,-11]`。

## 4. 参数（`chassis.yaml`）

| 参数 | 作用 | 当前值 | 状态 |
|---|---|---|---|
| `can_interface` | CAN 设备 | `can0` | ✅ |
| `board_id` | DJI 板 CAN ID 偏移 | `1` | ✅ |
| `limit_vel` | 速度上限 m/s | `1.0` | ✅ |
| `limit_acc` | 加速度上限 | `1.5` | ✅ 已生效 |
| `angular_z_sign` | 旋转方向符号 | `1.0` | ⚠️ 待实车确认方向 |
| `width` / `length` | **轮心到轮心**距离 | `0.44` | ❌ **占位，必须卷尺实测** |
| `wheel_radius` | 轮半径 | `0.075` | ⚠️ 待确认 |
| `ratio` | 减速比 | `1.0` | ✅ 必须 1.0 |
| `cmd_vel_timeout_ms` | 超时安全网 | `200` | ✅ 别调大 |

## 6. 四次调试教训（务必记住）

### 教训 1：日志说假话比没日志更糟

曾把能用的 `board_id: 1` 误改成 0，因为日志里写死了：

```cpp
RCLCPP_INFO(get_logger(), "底盘已使能 4 个电机（board_id=%u）", 0u);  // 恒为 0
```

**已修复**：`OmniChassis` 存下真实 `board_id_` 并打印。排查时**先确认日志是不是真的**。

### 教训 2：RX=0 不一定是"板子没回应"

CAN 计数里 `RX packets = 0` 曾被当成故障，但底盘**只发不读**——`VelCfg/MotorOn/VelCtrl`
都是写命令，从不调 `ReadInfo`，也没注册接收回调；DJI 板只在被查询时才回。

**判据是 TX 错误计数**：`TX 70 帧、errors 0、ERROR-ACTIVE` = 每帧都被 ACK = 板子在线。
别再看 `RX packets`。

### 教训 3：CAN 拔插后，板子的故障锁存只能靠断电清

见 §2.2。症状极有迷惑性，**软件侧全都正常**：

| 检查项 | 表现 |
|---|---|
| can0 | UP / ERROR-ACTIVE / 1Mbps ✅ |
| 底盘节点 | 在跑，`board_id=1` ✅ |
| 运动学 | 发 0.15 → 轮速 `[13,13,-13,-13]` ✅ |
| CAN 帧 | `201#01 00 07 00 1B 00 00 00`（±27，ID 正确）✅ |
| 板子 ACK | TX errors = 0 ✅ |
| **轮子** | **不动** ❌ |

**排查到这一层就该直接去断电重启电机板，别再翻软件了。**

### 教训 4：同时跑多个底盘节点会互相抢 CAN

`ros2 launch` 起一个节点。如果忘了关旧的又起一个，就会有**两个节点同时往 can0 写**
（实测踩过：一个是我抓帧时起的、一个是用户自己起的）。

**每次重启前先确认只有一个：**

```bash
pgrep -af "lib/rb_chassis/rb_chassis_node"     # 应该只有 1 个
pkill -f "[r]b_chassis"                        # 多了就全清
```

> ⚠️ **`[r]` 不能省！** 不加的话 `pkill -f "rb_chassis"` 会把**你敲这条命令的 shell 本身**
> 也匹配上并杀掉（命令里含 `rb_chassis` 字面量）。我就中过两次。
