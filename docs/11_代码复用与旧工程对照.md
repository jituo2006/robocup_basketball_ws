## 5. 修改后复用的关键边界

### 5.1 底盘：保留硬件体系，改变控制语义

旧来源是 `2025chassislib/src/base_chassis.cpp`、`omni_chassis.cpp` 及对应头文件；当前仍使用同一类体系，但源码不是原样复制。

- `src/rb_chassis/src/base_chassis.cpp:40`：速度指令新鲜度检查。
- 同文件 `:51`：使用并赋值 `std::clamp` 的返回值；`:62` 起应用斜率限制。
- `src/rb_chassis/src/omni_chassis.cpp:72`：指令超时进入停车分支。
- 同文件 `:102`：可配置的 `angular_z_sign_`；`:107` 调用抽出的 `omniWheelRpm`。
- `src/rb_chassis/include/chassis_lib/omni_kinematics.h`：当前运动学公式和车体系约定；该文件在所核查旧工程中没有同名来源。

远程历史还包含 `c6d82fc`（2026-10-03，超时后持续下发零速）以及 `bfa4397`（2026-10-09，定位过期保护与到位停稳）。因此，不能直接照旧 README 中“只发一次零速”的文字理解当前远程行为，也不宜拿旧控制代码覆盖现有实现。

尺寸、转向符号和速度约定的修改属于当前机器适配，不能因底层来自旧项目就认定旧标定值仍然适用。

### 5.2 CAN：沿用 `26_R1` 补丁版

当前 `src/rb_chassis/third_party/bupt_can.cpp` 与 `26_R1/src/bupt_can/src/bupt_can.cpp` 的逐行比较只有一个替换区间：旧文件第 41–42 行，对应当前第 41–44 行。

当前文件保留队列上限 `kMaxQueuedFrames`（`:110`）和丢弃积压队列逻辑（`:114`），并包含线程 `joinable()` 检查（`:43`、`:44`）。这支持“沿用旧补丁版并调整析构保护”，而非“重新编写 CAN 驱动”。

协议文件完全相同，但 `rb_launcher_node.cpp` 是新的 ROS 服务封装：`:81` 创建服务，`:93` 安排重连，`:111` / `:139` 捕获串口异常。`serial_port.cpp` 和串口头文件也有修改，不能把整个 `rb_launcher` 说成原封不动复制。

## 9. 后续整理与复用优先级

1. **先统一当前版本基准**：远程比本机新；本次仅增加文档，不同步、覆盖或合并代码。
2. **保留现有硬件驱动**：底盘、CAN 和机构协议已有明确来源，不需要再从零实现。
3. **优先评估旧投篮模型**：这是目前最明确的“已有资产但尚未接线”项；先核对数据与机构，再决定复用训练结果还是重新标定。
4. **硬件接回后验证接口**：检查电机编号/方向、CAN、串口帧、转速/角度单位、指令超时停车，以及 `/Odometry` 坐标和时延。
5. **按场景评估旧导航能力**：如需复杂轨迹规划，再逐模块评估 `26_R1` / `fsm26`；不直接混入整套旧状态机。

本说明依据上述文件对照、当前配置和构建元数据形成；它是代码来源与接线情况核查，不是整车性能或赛事规则合规性验收。

## 10. 专项回答：当前 RoboCup 是否沿用 2025 的导航、地图、路线控制？

**没有把 2025 的导航整套沿用。延续的是外部雷达定位输入链路；当前到点控制和任务导航是新实现，2025 的路线跟踪器没有接入。**

| 能力 | 2025 工程中发现的实现 | 当前 `robocup_basketball_ws` | 判断 |
|---|---|---|---|
| 雷达里程计/定位输入 | `Lidar_Odometry` 接入 `/Odometry` 并处理里程计；这是适配层，不等同于 SLAM 本身 | 启动外部 `/home/user/lidar_360` 的 FAST-LIO 链路，`rb_localization` 订阅 `/Odometry` | 延续雷达定位输入方案，但没有直接搬用旧 `Lidar_Odometry` 节点 |
| 地图生成与显示 | 2025 工作区内未看到独立完整 SLAM/地图规划包；外部 SLAM 的历史版本来源尚未追溯 | 外部 FAST-LIO 提供定位/点云，RViz 显示 `/Laser_map`、机器人位姿和 TF | 使用外部能力；当前 RViz 点云地图不能证明已具备栅格地图全局路径规划 |
| 路线/航点跟踪 | `LineTracking/include/follower.hpp`、`src/follower.cpp` 和 Python 跟踪脚本，含 waypoint/PID 控制 | 未找到 `LineTracking` / `line_tracking` 包引用；采用 `rb_mission` 的 `goto_command` 和到位确认 | 旧路线控制没有接入，当前实现不同 |
| 地图点击到点 | 不在本次旧工程复用证据中 | `/goal_pose` 或点击工具 → `/rb_mission/goto` → 当前控制器 | 是目标点驱动，不等同于计算完整可通行路线 |

当前控制链路可以理解为：

```text
外部雷达 / FAST-LIO
    ├─ 点云 → RViz 地图显示
    └─ /Odometry → rb_localization → 当前车体位姿
                                          ↓
点击目标 / 任务目标 → rb_mission → goto_command → /cmd_vel → rb_chassis
                                 └─ ArrivalGate：判断是否到位并停稳
```

`src/rb_mission/rb_mission/geometry.py:39` 的 `goto_command` 根据当前位置与目标位置计算速度，包含增益、接近限速和车体系转换。`navigation.py` 提供 `PoseFeedback` 与 `ArrivalGate`。它们不代表 A*/Dijkstra/Nav2 式全局地图规划；本次也没有找到 `nav2_bringup`、`nav2_msgs` 或 `nav2_simple_commander` 引用。

另外，旧 **2026 `26_R1`** 已有 `r1_navigation/PathFollower`、前视距离/横向误差参数、速度来源切换和红蓝方 YAML 路线。当前 RoboCup 也未引用 `r1_navigation`。因此，如果下一步希望复用更完整的既定路线跟踪能力，应先评估这个旧 2026 模块，而不是认为当前工程已经继承了它。

以上是代码结构与配置核查，不是今天的实车导航测试。外部 FAST-LIO 是否与 2025 使用的版本同源，需要进一步追溯其仓库版本，不能仅凭同一话题名下结论。
