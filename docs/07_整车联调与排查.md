# 07 · 整车联调与排查

> **原则**：一次只点亮一层，每层验收通过再走下一层。
> 顺序：**底盘 → 机构 → 相机/感知 → 定位 → 整车**。各模块细节见 01~06。

## 0. ⚠️ 安全规程（第一次让车上路前**必须**读）

> 背景：一次遥控终端意外断开，机器人在**没人看着**的状态下留在了原地。
> 那次恰好安全（底盘跑的是 `dry_run`，且进程全停），但说明流程有洞。

### 0.1 三层停机手段，从快到慢

| # | 手段 | 生效时间 | 说明 |
|---|---|---|---|
| 1 | **按车上电源开关** | 立即 | **最可靠，永远优先。软件永远不如拔电** |
| 2 | `bash tools/panic.sh` | ~2 s | 锁 estop → 发零速 → 杀 mission/chassis；`--hard` 再把 `can0` 拉低 |
| 3 | `/cmd_vel` 200ms 超时 | 0.2 s | **底盘内置**：收不到指令就自动发零轮速（配置里 `cmd_vel_timeout_ms: 200`，**不要调大**） |

**第 3 条是最重要的兜底**：即使上位机整个挂了，只要底盘节点还活着，它 0.2 秒内就会停车。

### 0.2 第一次上路：轮子架空

让车第一次真正驱动电机之前，**把驱动轮架空**：

1. 架起来，`dry_run:=false` 起底盘
2. 发一个正前方目标 → **四轮应同向向前转**
3. 发一个右侧目标 → **车体应向右转**
4. 方向不对立刻停，别落地

### 0.3 dry_run → 真机的切换要有意识

```bash
ros2 launch rb_chassis chassis.launch.py dry_run:=true    # 只解算，电机不动
ros2 launch rb_chassis chassis.launch.py                  # 默认 false = 真发 CAN
```

**验证链路时一律用 `dry_run:=true`。** 确认 `/cmd_vel`、轮速解算都对，
再切真机 —— 中间不要"顺手"跳步。

### 0.4 遥控终端断开会怎样（重要）

| 场景 | 车会怎样 |
|---|---|
| 上位机进程全死 | 车**不动**（没人把 `/cmd_vel` 变成 CAN） |
| mission 死了、chassis 活着 | chassis 200ms 超时 → **停车** ✅ |
| **mission 和 chassis 都活着** | ⚠️ 它会**继续执行最后一个目标** —— 这才是真危险 |

最后一行就是"断线后车还在跑"的唯一路径。防范：

- **用 `tmux` 跑驱动栈**，断线后能重新 `tmux attach` 回去处置
  ```bash
  tmux new -s drive        # 起一个会话
  # Ctrl-b 然后 d          # 脱离（进程继续跑）
  tmux attach -t drive     # 重新接上
  ```
- **始终留一个终端**,里面 `bash tools/panic.sh` 已就绪（或 `history` 里第一条）
- **别让车在没人看着时自主行驶** —— 规则允许自主，但练习时人要在场

### 0.5 ⚠️⚠️ 千万别 `kill -9` 底盘 —— 会把电机板锁死

**电机板的看门狗靠"持续收到 CAN 帧"喂。** 一旦断粮，板子进入"通信超时"故障：

- 表现为：**CAN 正常发帧、日志说"底盘已使能 4 个电机"、但电机就是不转**
- **软件清不掉**（`MotorOn` 也没用），**只能给电机板断电 10 秒**
- 这是原始硬件设计，不是我们的 bug

**哪些操作会断粮：**

| 操作 | 会锁吗 |
|---|---|
| `kill -9 <底盘进程>` | ❌ **会锁** |
| 关终端（SIGHUP 杀掉底盘） | ❌ 会锁 |
| 让底盘停很久不动 | ❌ 会锁 |
| 切任务到 IDLE（底盘继续发零速） | ✅ 不会 |
| `bash tools/panic.sh`（它保留零速下发） | ✅ 不会 |
| Ctrl-C 优雅退出（走析构，发 MotorOff） | ✅ 不会 |

**所以：停车的正确方式是"切 IDLE"或 `panic.sh`，不是杀进程。**

> 代码已经加固：`omni_chassis.cpp` 在 `cmd_vel` 超时后**每周期都发零速**
> （原来只发一次，之后停发，板子照样锁）。

## 2. 整车启动（主机重启后的标准流程）

> **每场比赛/每次开机都走这一遍**，顺序不能反。

### 2.1 三条"做一次就好"的永久配置（已就绪，重启不丢）

| 项 | 状态 | 文件 |
|---|---|---|
| 雷达网卡静态 IP `192.168.1.110/24` | ✅ NetworkManager 的 `Wired connection 1`，`autoconnect=yes`（插网线自动配） | — |
| CAN 自动拉起（PCAN 插上即 1Mbps/qlen20/UP） | ✅ udev 规则 | `/etc/udev/rules.d/99-can0.rules` + `/usr/local/sbin/can0_setup.sh` |
| SSH 推送（不用再输令牌） | ✅ `git remote` 已改 SSH | `~/.ssh/config`（走 `ssh.github.com:443` 代理） |

### 2.2 每次开机的正确顺序

```
① 主机开机
② 合上总开关（雷达 + 电机板 + 相机一起上电）
③ bash tools/boot.sh          ← 唯一需要敲的命令
④ 等约 30 秒
⑤ bash tools/check_ready.sh   ← 全绿才继续
⑥ 开地图 / 开车
```

**⚠️ 为什么是"先合开关、再跑 boot.sh"：**
底盘节点启动时会发一次 `MotorOn` 使能电机 —— 必须在**电机板已经上电之后**发。
反了（先起软件、后合开关）这条使能命令落到还没上电的板子上就丢了，车不动。

### 2.3 `tools/boot.sh` 做了什么（三步）

```
[1/3] 清理残留进程（防止重复驱动抢端口）   ← 最关键
[2/3] 检查 CAN（udev 应已自动做，这里兜底）
[3/3] 起整套软件（前台，日志直接刷屏；Ctrl-C 停）
```

> **[1/3] 为什么必须清残留**：launch 重启时 livox 驱动常常不被带走，变成孤儿进程。
> 第二个驱动起来后**两个进程同时持有 56301/56401 端口**（SO_REUSEPORT），
> 内核把雷达 UDP 数据随机分给两个进程 → 点云时有时无、IMU 丢失、地图消失。
> **看起来像"雷达坏了"，其实是重复驱动抢端口** —— 这是本次排查最大的坑。
> `boot.sh` 每次启动前 `kill -9` 清干净，保证"只有一个"。

### 2.6 ⚠️ 硬件重启的两条铁律

| 你做了什么 | 要不要动电源 |
|---|---|
| 只重启某个节点（mission 等） | **不用动电源** |

## 4.5 定位 → 底盘 全链验证（dry-run，车不会动）

改完代码、上车之前，先用这条**不需要 CAN 适配器**的链路确认"算得对"：

```bash
# ① 底盘先跑 dry-run（只解算，不下发 CAN）
ros2 launch rb_chassis chassis.launch.py dry_run:=true

# ② 确认 /cmd_vel 两头都通（关键：Subscription 必须是 1）
ros2 topic info /cmd_vel        # Publisher 1 / Subscription 1

# ③ 底盘参数对不对（轮距/轮径必须是实测值，不是默认值）
#    日志应打印：底盘参数: 限速=1.00 轮距=0.440x0.440 轮径=0.075

# ④ 在 RViz 地图上点一下（或发 /goal_pose），看两处：
ros2 launch rb_bringup rviz_map.launch.py
#    a) /cmd_vel 有速度输出          → 任务侧算对了
#    b) 底盘 debug 日志有 wheels=[...] → 运动学解算对了
```

开底盘 debug 日志看轮速：

```bash
ros2 run rb_chassis rb_chassis_node --ros-args -r __node:=rb_chassis \
  --params-file install/rb_chassis/share/rb_chassis/config/chassis.yaml \
  -p dry_run:=true --log-level debug
# 输出：vx=0.343 vy=0.036 wz=0.000 wheels=[27 34 -27 -34]
```

**手算核对**：`wheel = (±vx·c ± vy·c − wz·arm)·factor`，
`c=cos45°`、`factor=60/(2π·轮径)`、`arm=hypot(轮距/2, 轴距/2)`。

### 4.6 ⚠️⚠️ 改完代码**必须重启节点**（本次踩的坑）

ROS 2 节点**在启动时**把 Python 文件读进内存。`colcon build` 只更新磁盘上的文件，
**不会**影响已经在跑的进程 —— 哪怕用了 `--symlink-install` 也一样。

**实测代价**：修好避障的 bearing 符号后，忘了重启 `mission_node`，
结果它已经跑了 1 小时 17 分（用的是旧代码），导致验证时 `vy` 符号仍然是反的，
一度怀疑"修复本身错了"。

```bash
# 判断某个节点是不是在跑旧代码：比对启动时刻与文件修改时刻
ps -eo pid,lstart,etime,cmd | grep <节点名>
stat -c '%y' src/<包>/<包>/<文件>.py
```

**改完代码后的标准动作**：

```bash
colcon build --symlink-install
# 然后**杀掉并重起**相关节点（launch 起的就整个重起 launch）
```

> 只重启"改了代码的那个节点"通常就够，但 launch 文件管理的节点整组重起更省心。

## 5. 排查树

> **万能第一步：`bash tools/check_ready.sh`。** 它会一次查完 CAN / 雷达 / IMU /
> 点云 / 里程计 / 定位 / 发散，直接告诉你是哪一层坏了。

### 5.1 "地图又没了" —— 三层口诀（**别一上来就断电雷达**）

这个问题反复踩了很多次。按**从下往上**查，对症下药：

```bash
# ① 雷达发数据吗（网络层，最底层）
sudo timeout 3 tcpdump -i enp114s0 -nn udp and host 192.168.1.138 -c 3
# ② 驱动开数据端口吗（56301=点云、56401=IMU）
ss -lunp | grep -E "56301|56401"
# ③ 话题有数据吗
ros2 topic hz /livox/lidar     # 注意：要先 source 雷达工作空间，否则认不出 CustomMsg
ros2 topic hz /livox/imu       # 应 ~200Hz
```

| ①雷达发 | ②端口 | ③话题 | 判断 → 做法 |
|---|---|---|---|
| ✅ | ❌ | ❌ | **驱动卡死**（多半是重复驱动）→ `bash tools/boot.sh` 清残留重起 |
| ✅ | ✅ | ❌ | 驱动 ROS 侧有问题 → 重起驱动 |
| ❌ | — | — | 雷达真的没流 → 这时才考虑断电重启雷达 |
| ✅ | ✅ | ✅ | 数据正常 → 查 §5.2 发散 / §5.3 TF |

**两个高频坑：**

1. **重复驱动抢端口**（最常见！）：`ps -eo pid,cmd | grep livox_ros_driver2_node`
   看到 2 个以上就是它 —— 两个进程同时持有 56301/56401（SO_REUSEPORT），
   雷达数据被随机分发 → 点云时有时无、IMU 丢失。
   **做法：`bash tools/boot.sh`（会自动清残留）。**
2. **孤儿驱动卡死**：父 launch 死了但驱动还在（ppid=1）。`kill`（SIGTERM）有时杀不掉，
   要 `kill -9`，再重起驱动。**不用动雷达电源。**

> **教训**：曾经一直让人"断电重启雷达"，其实根因是重复驱动。**先查端口，再决定动不动电源。**

### 5.2 位姿乱飘 / 点云出现"几千公里外的异常点" = **FAST-LIO 发散**

**症状**：RViz 里位姿箭头来回飘；点云形状对但整体被平移到几千公里外；
`/Odometry` 的 x/y/z 是几千甚至上万米，而且**数值持续增大**。

**判据**（`check_ready.sh` 会自动检）：

```bash
ros2 topic echo /Odometry --once --field pose.pose.position
# 正常：x 在 ±10m 内；发散：x 是 -4000 这种，且越跑越大
```

**原因**：FAST-LIO 靠几何特征配准，**空房间（平墙、没东西）特征太少会跟丢发散**。
比赛场地有篮筐/柱子/围栏，概率低很多。

**修复：发散不可逆，只能重启 FAST-LIO。**

```bash
bash tools/boot.sh     # 简单粗暴，整套重起
```

### 5.3 车不动？

```
车不动？
├─ 先跑 bash tools/check_ready.sh —— 一次看完全链
├─ 任务节点死了？ ros2 topic info /goal_pose → Subscription 必须是 1
│   （是 0 说明 mission 没在跑，点了地图没任何节点接收）
├─ /cmd_vel 有数据吗 → 没有 = 遥控没起，或 mission 卡在等定位/视觉
│                     （ros2 topic info /cmd_vel：Publisher 和 Subscription 都要是 1）
├─ 有数据 + CAN 在发帧 + 车不动 → **电机板锁死**，只能断电 10 秒
│   验证 CAN 确实在发：candump can0 | head
│     应看到 cmd=03(VelCfg) / 01(MotorOn) / 07(VelCtrl)
│   验证总线健康：ip -s -d link show can0 → TX errors 必须是 0
│   ⚠️ 板子是只写的：RX=0 正常，别管
└─ 动但方向不对    → 尺寸参数没量对 / angular_z_sign 反了
```

**⚠️ 为什么板子会锁**：电机板的看门狗靠"持续收到 CAN 帧"喂。
**反复 `kill -9` 底盘**、或让底盘停很久，板子就断粮锁死。
`omni_chassis.cpp` 里已经改成"超时后每周期都发零速"，只要底盘活着就不会锁。

### 5.4 每次导航都冲过目标点 / 地图位置严重滞后

**不是判据错，是反馈延迟。** 一条命令测：

```bash
rbws
python3 tools/check_latency.py
```

```
✓ /Odometry          24.0 ms   FAST-LIO 里程计（定位的输入）
✓ /localization/pose  0.6 ms   定位输出（任务实际用的）
✅ 延迟健康（<100ms）
```

健康值：**100ms 以内**。几百毫秒到几秒就是下面两个原因。

> ⚠️ **测量本身的坑**：不要在一个脚本里同时订阅大点云
> （`/cloud_registered`、`/livox/lidar`）—— 脚本自己处理不过来，
> 读数会被自己抬高 5~10 倍（实测：只订阅 `/Odometry` 是 24ms，
> 同时订阅 5 个话题变成 141ms）。`check_latency.py` 默认只订阅轻量话题；
> 要点云延迟加 `--with-cloud`，并记住那是**上界**。

#### 原因 A：别的节点把 CPU 吃光（实测踩坑）

```bash
uptime                                    # load average 应 < 16（核数）；实测出过 29
ps -eo pcpu,pid,comm --sort=-pcpu | head  # 看谁在吃 CPU
```

实测 `perception_node` 占 **1139% CPU（11.4 核）** —— ONNX Runtime 默认吃满所有核，
把 FAST-LIO 饿死 → `/Odometry` 时延飙到 **2.2 秒**。
**已修**：`detectors.py` 给 `InferenceSession` 传 `SessionOptions` 限线程
（`perception.yaml` 的 `intra_op_threads: 2`）。效果：1139% → 271%。

#### 原因 B：FAST-LIO 处理跟不上

```bash
ros2 topic hz /livox/lidar        # 输入 ~10Hz
ros2 topic hz /cloud_registered   # 输出若明显低于输入 = 跟不上 → 延迟持续累积
```

实测输出只有 **5.4Hz**（输入 10Hz），导致延迟累积到 2.2s。
**已调 `~/lidar_360/.../FAST_LIO_WITH_PROPAGATE/config/mid360.yaml`**（只改参数，不动代码）：

| 参数 | 原来 | 现在 | 作用 |
|---|---|---|---|
| `point_filter_num` | 1（每点都用） | **2** | 减半点数 |
| `filter_size_surf/map` | 0.15 | **0.20** | 降采样更粗 |
| `det_range` | 100.0 | **40.0** | 只留 40m（房间/场地够） |
| `path_en` | true | **false** | 我们不用 `/path` |
| `scan_bodyframe_pub_en` | true | **false** | 不用车体系点云 |

**效果汇总：**

| 指标 | 修复前 | 现在 |
|---|---|---|
| `/Odometry` 时延 | 2291 ms | **24 ms** |
| `/cloud_registered` 时延 | 441 ms | **28 ms** |
| 点云输出速率 | 5.4 Hz | **10.0 Hz** |

#### 延迟降下来后，"接近限速"可以放宽

```yaml
limits:
  approach_radius_m: 0.40   # 进入这个半径开始限速
  approach_speed: 0.25      # 接近时的速度上限 m/s
  position_tolerance: 0.05  # 到点判据 m
```

**这三个值是随延迟一起标定的**：延迟 2291ms 时只能设 `speed=0.12 / tol=0.10`；
延迟降到 24ms 后超调只剩 `0.024 × 0.25 ≈ 0.6cm`，所以
**放宽速度**（最后一段快了 2 倍）**并收紧容差**（原来 0.10m 意味着
"停在离目标 10cm 内任意位置" —— 那就是"到点不准"）。

| 现象 | 调哪里 |
|---|---|
| 还冲过头 | `approach_speed` 调小（0.15） |
| 到点还差几厘米 | `position_tolerance` 调小（0.03）；查底盘尺寸是否实测 |
| 最后一段磨蹭 | `approach_speed` 调大（0.35） |

### 5.4b 🐛 审查出的两个真 BUG（已修，附回归测试）

#### BUG 1 · yaw 取错源：把**高度**当成了朝向

```python
# 曾经（localization_node.py / mission_node.py 各一份）
if abs(hypot(q.x, q.y, q.z)) < 1e-6:
    yaw = pos.z        # ← FAST-LIO 的 pos.z 是【高度】(实测 -0.007 m)！
```

**FAST-LIO 的 `pose.position.z` 是高度，不是 yaw。** "yaw 塞在 z 里" 只是
本队自家消息的老约定，对第三方里程计不成立。

机器人朝向≈0° 时四元数的 x,y,z **恰好都是 0**，于是走进分支把高度当朝向；
高度一漂朝向就漂 → 车体系速度方向错 → **过冲 / 往回走**。

**已修**：判据改用四元数**模长**（`hypot(q.x,q.y,q.z,q.w)`≈1 = 有效旋转），
只有四元数全零（自家老消息）才退回 `position.z`。
抽成公共函数 `rb_mission.geometry.yaw_from_pose_msg`，配 4 条回归测试
（含"高度 0.5m 时不能返回 0.5 rad"），**反向验证：把旧判据放回去测试立刻失败**。

#### BUG 2 · 底盘对 /cmd_vel **重复旋转**（潜伏）

```cpp
// omni_chassis.cpp 曾经无条件执行：
const double vx = cmd.linear.x*cos(yaw) + cmd.linear.y*sin(yaw);   // R(-yaw)
```

任务侧 `goto_command` **已经**输出车体系速度（内部做了 `R(−yaw)`）。
底盘再转一次 = **双重旋转**。手算验证（yaw=90°）：

| 步骤 | 结果 |
|---|---|
| 目标在场地系正前方 | 世界速度 (0.4, 0) |
| 任务侧转车体系（机器人朝左） | → (0, **−0.4**) 向右平移 ✅ |
| 底盘又转一次 | → (**−0.4**, 0) **往后退** ❌ |

**现在没发作**，因为 `/odom` 没人发布（底盘 `has_odom_=false` → yaw=0 → 不转）。
**但只要谁发 `/odom`，车就会朝错方向走。**

**已修**：按 ROS 标准 `/cmd_vel` = 车体系，**默认不旋转**；旋转变成配置项
`chassis.yaml` 的 `cmd_vel_frame: body|world`（默认 `body`），只给确实发
场地系速度的外部发布者用。

### 5.8 RViz 画面卡顿 / "地图不实时"（VNC 软件渲染）

**先分清是"数据慢"还是"画面慢"：**

```bash
python3 tools/check_latency.py     # 数据侧。健康 = <100ms
ps -eo pcpu,pid,comm --sort=-pcpu | head    # 看 rviz2 占多少 CPU
```

实测过：数据侧 24ms（很好），但 **rviz2 占 363% CPU** —— 画面是 CPU 一点点
画出来的，所以"看着卡"。根因：

- 这台机器跑在 **VNC 虚拟显示器（`DISPLAY=:2.0`）** 上，VNC 只提供**软件 GLX**
  → RViz 加载 `swrast`，用 CPU 渲染 3D（`grep swrast /proc/$(pgrep -x rviz2)/maps`）
- 机器有 Intel 核显、`/dev/dri/card0` 也在、用户也在 `video` 组，
  **但 VNC 会话用不上它**

**已做的优化**（`src/rb_bringup/rviz/map_goto.rviz`）：

| 项 | 原来 | 现在 | 理由 |
|---|---|---|---|
| `Frame Rate` | 30 | **10** | 数据本来只有 10Hz，30FPS 是纯浪费（软件渲染最大头） |
| `Decay Time` | 5 | **3** | 累积点数 ~46 万 → ~28 万 |
| `Point Size` | 2 | **1** | 每点填充像素减半 |
| `Plane Cell Count` | 20 | **12** | 网格线变少 |

效果：**rviz2 363% → 161% CPU**，load average 11.6 → 9.8。

**还可以更狠（按需）：**
- 直接**不开 RViz**开车（比赛不需要它），或把它跑在**另一台笔记本**上（`ROS_DOMAIN_ID` 相同即可）。
- 把 `mid360.yaml` 的 `dense_publish_en` 设 `false`（点云 9259 → 1233 点/帧，地图变稀但更轻）。

### 5.7 RViz 点云颜色怎么看

点云显示用的是 `Color Transformer: AxisColor` —— **按高度上色**：

| 高度 | 颜色 |
|---|---|
| 地板（最低） | **橙红** ← 常被误认为"异常点" |
| 墙壁（中） | 绿/黄 |
