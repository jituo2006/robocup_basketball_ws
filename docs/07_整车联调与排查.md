# 07 · 整车联调与排查

> **原则**：一次只点亮一层，每层验收通过再走下一层。
> 顺序：**底盘 → 机构 → 相机/感知 → 定位 → 整车**。各模块细节见 01~06。

---

## 0. ⚠️ 安全规程（第一次让车上路前**必须**读）

> 背景：一次遥控终端意外断开，机器人在**没人看着**的状态下留在了原地。
> 那次恰好安全（底盘跑的是 `dry_run`，且进程全停），但说明流程有洞。

### 0.1 三层停机手段，从快到慢

| # | 手段 | 生效时间 | 说明 |
|---|---|---|---|
| 1 | **按车上电源开关** | 立即 | **最可靠，永远优先。软件永远不如拔电** |
| 2 | `bash tools/panic.sh` | ~2 s | 锁 estop → 发零速 → 杀 mission/chassis；`--hard` 再把 `can0` 拉低 |
| 3 | `/cmd_vel` 200ms 超时 | 0.2 s | **底盘内置**：收不到指令就自动发零轮速（配置里 `cmd_vel_timeout_ms: 200`，**不要调大**） |

**第 3 条是最重要的兜底**：即使上位机整个挂了，只要底盘节点还活着，它 0.2 秒内就会停车。

### 0.2 第一次上路：轮子架空

让车第一次真正驱动电机之前，**把驱动轮架空**：

1. 架起来，`dry_run:=false` 起底盘
2. 发一个正前方目标 → **四轮应同向向前转**
3. 发一个右侧目标 → **车体应向右转**
4. 方向不对立刻停，别落地

### 0.3 dry_run → 真机的切换要有意识

```bash
ros2 launch rb_chassis chassis.launch.py dry_run:=true    # 只解算，电机不动
ros2 launch rb_chassis chassis.launch.py                  # 默认 false = 真发 CAN
```

**验证链路时一律用 `dry_run:=true`。** 确认 `/cmd_vel`、轮速解算都对，
再切真机 —— 中间不要"顺手"跳步。

### 0.4 遥控终端断开会怎样（重要）

| 场景 | 车会怎样 |
|---|---|
| 上位机进程全死 | 车**不动**（没人把 `/cmd_vel` 变成 CAN） |
| mission 死了、chassis 活着 | chassis 200ms 超时 → **停车** ✅ |
| **mission 和 chassis 都活着** | ⚠️ 它会**继续执行最后一个目标** —— 这才是真危险 |

最后一行就是"断线后车还在跑"的唯一路径。防范：

- **用 `tmux` 跑驱动栈**，断线后能重新 `tmux attach` 回去处置
  ```bash
  tmux new -s drive        # 起一个会话
  # Ctrl-b 然后 d          # 脱离（进程继续跑）
  tmux attach -t drive     # 重新接上
  ```
- **始终留一个终端**,里面 `bash tools/panic.sh` 已就绪（或 `history` 里第一条）
- **别让车在没人看着时自主行驶** —— 规则允许自主，但练习时人要在场

### 0.5 上路前 30 秒检查

```bash
ros2 topic info /cmd_vel     # Publisher 1 / Subscription 1
# 底盘日志确认：dry_run 是否为你想要的、轮距/轮径是否为实测值
# 手上/脚边确认：电源开关位置
# 另开一个终端：bash tools/panic.sh   （准备好，先别按）
```

## 4.5 定位 → 底盘 全链验证（dry-run，车不会动）

改完代码、上车之前，先用这条**不需要 CAN 适配器**的链路确认"算得对"：

```bash
# ① 底盘先跑 dry-run（只解算，不下发 CAN）
ros2 launch rb_chassis chassis.launch.py dry_run:=true

# ② 确认 /cmd_vel 两头都通（关键：Subscription 必须是 1）
ros2 topic info /cmd_vel        # Publisher 1 / Subscription 1

# ③ 底盘参数对不对（轮距/轮径必须是实测值，不是默认值）
#    日志应打印：底盘参数: 限速=1.00 轮距=0.440x0.440 轮径=0.075

# ④ 在 RViz 地图上点一下（或发 /goal_pose），看两处：
ros2 launch rb_bringup rviz_map.launch.py
#    a) /cmd_vel 有速度输出          → 任务侧算对了
#    b) 底盘 debug 日志有 wheels=[...] → 运动学解算对了
```

开底盘 debug 日志看轮速：

```bash
ros2 run rb_chassis rb_chassis_node --ros-args -r __node:=rb_chassis \
  --params-file install/rb_chassis/share/rb_chassis/config/chassis.yaml \
  -p dry_run:=true --log-level debug
# 输出：vx=0.343 vy=0.036 wz=0.000 wheels=[27 34 -27 -34]
```

**手算核对**：`wheel = (±vx·c ± vy·c − wz·arm)·factor`，
`c=cos45°`、`factor=60/(2π·轮径)`、`arm=hypot(轮距/2, 轴距/2)`。

### 4.6 ⚠️⚠️ 改完代码**必须重启节点**（本次踩的坑）

ROS 2 节点**在启动时**把 Python 文件读进内存。`colcon build` 只更新磁盘上的文件，
**不会**影响已经在跑的进程 —— 哪怕用了 `--symlink-install` 也一样。

**实测代价**：修好避障的 bearing 符号后，忘了重启 `mission_node`，
结果它已经跑了 1 小时 17 分（用的是旧代码），导致验证时 `vy` 符号仍然是反的，
一度怀疑"修复本身错了"。

```bash
# 判断某个节点是不是在跑旧代码：比对启动时刻与文件修改时刻
ps -eo pid,lstart,etime,cmd | grep <节点名>
stat -c '%y' src/<包>/<包>/<文件>.py
```

**改完代码后的标准动作**：

```bash
colcon build --symlink-install
# 然后**杀掉并重起**相关节点（launch 起的就整个重起 launch）
```

> 只重启"改了代码的那个节点"通常就够，但 launch 文件管理的节点整组重起更省心。

## 5. 排查树

```
车不动？
├─ 先跑 tools/can_recover.sh —— 它会查 can0 状态 + 清掉重复的底盘节点
│   （拔插过 CAN 适配器的话，大概率就是它，见 docs/03 §2.2）
├─ /cmd_vel 有数据吗 → 没有 = 遥控没起，或 /mission/status 卡在等定位/视觉
│                     （用 ros2 topic info /cmd_vel：Publisher 和 Subscription 都要是 1）
├─ 有数据不动      → ① can0 是 UP 吗（拔插后会变 DOWN）
│                     ② 是不是有多个底盘节点在抢 CAN
│                     ③ **电机板断电 10 秒再上电**（故障锁存只能靠断电清）
│                     判据：TX 错误计数 = 0 才算通信正常；RX=0 是正常的，别管
└─ 动但方向不对    → 尺寸参数没量对 / angular_z_sign 反了

定位飘？
├─ /localization/ok 是 true 吗
├─ landmarks 填了吗（空了视觉方位角不生效）
└─ 静止漂 → 里程计噪声大 或 绝对观测没生效

视觉看不到？
├─ /perception/detections 有对应 label 吗
│   ├─ 有目标没框 → 阈值/模型问题
│   └─ 看不到     → 相机曝光/视野，不是算法问题
└─ view_camera.py 里能看到吗
```
